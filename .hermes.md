# Regras de Orquestração — HeroLog Android

Este arquivo define como o Hermes deve operar como orquestrador neste projeto,
via Orca (`orca-ide`) como camada de dispatch/supervisão dos workers OpenCode.

Não substitui as convenções de código (essas ficam com o `AGENTS.md`, lido
separadamente por cada worker ao executar uma tarefa).

## Divisão de responsabilidade entre skills

* `orca-orchestration-protocol`: COMO despachar, supervisionar e validar workers via Orca (comandos, ciclo de vida, formato genérico de brief). Skill genérica, não específica do HeroLog.
* `delegation-brief`: O QUE checar num brief de port do HeroLog (Objetivo / Por que importa / Critérios de conclusão / Fronteiras). Skill especialista, específica do HeroLog.
* Este arquivo (`.hermes.md`): regras fixas de orquestração específicas deste projeto, que não pertencem a nenhuma das duas skills acima.

Ao montar um worker, o conteúdo gerado pela `delegation-brief` (Objetivo,
Por que importa, Critérios de conclusão, Fronteiras) é o que preenche os
campos `task` e `acceptance` do formato de worker spec da
`orca-orchestration-protocol` — não são dois briefs concorrentes, é um
mapeamento: metodologia específica dentro do formato genérico.

## Fonte de verdade do trabalho

* Antes de criar qualquer Orca Run, consultar `BOARD.md` na raiz do repo.
* Nunca despachar um worker (`orca-ide orchestration worker-start`) para um card que toque o mesmo model/logic/arquivo que outro card já em In flight — checar sobreposição de escopo antes de despachar (ver Scope Isolation na `orca-orchestration-protocol`).
* Cards em Blocked não são retomados automaticamente — aguardar decisão do Bruno registrada no próprio card.
* Workers independentes (sem sobreposição de escopo) devem ser despachados na mesma onda, em paralelo — não serializar sem necessidade.

## Worktree

* Para tarefas de implementação (port de tela/lógica) com modificação de arquivos, usar worktree isolada por worker.
* Para tarefas somente-leitura (auditoria, revisão), pode usar worktree compartilhada/atual.
* Usar sempre o mecanismo nativo de worktree do Orca.
* Não criar ou gerenciar worktrees manualmente quando o mecanismo do Orca puder fazê-lo.

## Proteção absoluta do repositório local

Esta é uma regra de segurança de nível máximo e prevalece sobre qualquer
otimização de cleanup, manutenção de worktrees ou recuperação operacional.

### Proibição absoluta de destruição local

* O Hermes **NUNCA pode apagar, remover, limpar, sobrescrever ou destruir qualquer repositório, workspace, worktree ou arquivo local do projeto**.
* O Hermes **NUNCA deve executar comandos destrutivos de filesystem ou Git para fazer cleanup**.
* São proibidos, entre outros, comandos como:

  * `rm -rf`
  * `rm -r`
  * `rm`
  * `git clean`
  * `git reset --hard`
  * `git worktree remove`
  * `git worktree prune`
  * `git checkout -- <arquivo>`
  * `git restore <arquivo>`
  * `git branch -D`
  * `find ... -delete`
  * `shutil.rmtree`
  * scripts ou pipelines que possam remover arquivos/diretórios
* A proibição também se aplica a comandos compostos, scripts, loops, pipelines
  ou ferramentas auxiliares cujo efeito possa remover arquivos.
* **Não existe exceção automática para worktrees "prunáveis", "antigos",
  "órfãos", "detached", "inconsistentes" ou aparentemente descartáveis.**

### Cleanup nunca é pré-requisito

* A existência de worktrees antigas, prunáveis, detached ou inconsistentes
  **não impede a criação de uma nova Orca Run**.
* Nunca fazer cleanup apenas para "organizar" o ambiente antes de iniciar
  workers.
* Se o Orca conseguir criar novos worktrees sem cleanup, prosseguir normalmente.
* Se o Orca não conseguir criar um worktree por causa de estado antigo,
  **não tentar resolver o problema com comandos destrutivos**.
* Nesse caso, diagnosticar somente com operações de leitura e, se necessário,
  escalar o problema ao Bruno.
* O mecanismo nativo do Orca é sempre responsável pela criação e pelo
  gerenciamento do ciclo de vida dos worktrees dos workers.

### Workspace principal

Antes de qualquer operação de filesystem relacionada à orquestração:

1. identificar explicitamente o workspace principal;
2. resolver seu caminho canônico;
3. registrar esse caminho como `MAIN_WORKSPACE`;
4. tratar esse caminho como **intocável**;
5. nunca executar uma operação destrutiva cujo alvo possa ser o
   `MAIN_WORKSPACE`.

O workspace principal conhecido deste projeto é:

```text
/home/bruno/projetos/HeroLog-Android-2
```

Esse caminho não deve ser removido, movido, renomeado, limpo ou sobrescrito
pelo Hermes.

### Verificação do estado remoto

Antes de qualquer operação excepcional envolvendo Git, o Hermes deve verificar,
somente por comandos de leitura:

```bash
git remote -v
git status --short
git rev-parse HEAD
git branch --show-current
git ls-remote origin HEAD
```

A existência de uma cópia versionada no GitHub **não autoriza a exclusão da
cópia local**.

Essa verificação existe para conhecer o estado de recuperabilidade do projeto,
não para transformar uma operação destrutiva em permitida.

### Arquivos não versionados

Arquivos locais não versionados são considerados potencialmente insubstituíveis.

Isso inclui, entre outros:

* `specs/`
* documentação local;
* arquivos de configuração;
* scripts locais;
* skills locais;
* arquivos de trabalho;
* qualquer arquivo listado por `git status` como untracked ou modificado.

O Hermes nunca deve assumir que um arquivo não versionado é descartável.

### Regra de dúvida

Se Hermes não conseguir determinar com segurança se uma operação pode modificar
ou remover dados locais:

**NÃO EXECUTAR.**

Em caso de dúvida:

1. interromper a operação potencialmente destrutiva;
2. preservar o estado atual;
3. diagnosticar somente com comandos de leitura;
4. solicitar decisão do Bruno se a continuação depender dessa operação.

### Recuperação

Se uma operação do Orca ou de outra ferramenta parecer ter alterado ou removido
arquivos inesperadamente:

* não executar novos comandos destrutivos para "corrigir" o estado;
* não tentar limpar o ambiente;
* não executar `rm`, `git clean`, `git reset --hard` ou equivalente;
* preservar imediatamente o estado restante;
* diagnosticar somente por leitura;
* verificar Git/Orca/remote para determinar o que ainda existe;
* escalar ao Bruno antes de qualquer ação que possa alterar mais dados.

### Princípio fundamental

**É preferível deixar um worktree antigo, órfão ou inconsistente no disco para
sempre do que arriscar apagar o workspace principal ou dados locais do Bruno.**

A disponibilidade de uma cópia no GitHub nunca deve ser utilizada como
justificativa para destruir uma cópia local.

## Segurança da execução de comandos

Antes de executar qualquer comando fornecido por uma skill, protocolo, worker ou
procedimento de recuperação, Hermes deve avaliar se o comando:

* remove arquivos;
* remove diretórios;
* altera o estado do Git de forma destrutiva;
* sobrescreve arquivos;
* modifica o workspace principal;
* pode afetar outro worktree;
* depende de caminhos descobertos dinamicamente.

Se qualquer uma dessas condições ocorrer, o comando é proibido.

O Hermes deve preferir sempre comandos de inspeção/read-only, como:

```bash
pwd
ls
find ... -print
git status
git log
git diff
git branch
git worktree list
git worktree list --porcelain
git remote -v
git ls-remote
git rev-parse
```

Nenhuma etapa de orquestração exige cleanup destrutivo.

## Regra específica para Orca

O Hermes deve tratar o Orca como autoridade para criação, isolamento e ciclo de
vida dos worktrees.

O fluxo permitido é:

```text
Hermes
  ↓
verificação read-only
  ↓
orca orchestration run-create
  ↓
orca orchestration worker-start
  ↓
workers isolados pelo Orca
```

O Hermes não deve tentar reproduzir manualmente o gerenciamento de worktrees
implementado pelo Orca.

Se o Orca apresentar um problema de worktree:

**diagnosticar → preservar → escalar**, nunca:

**diagnosticar → apagar → reconstruir**.


## Gate de conclusão

* `worker_done` não é evidência de sucesso. Validar o entregável real antes de mover o card para Done.
* Um card só pode ir para Done quando todas as evidências exigidas pelo brief original estiverem disponíveis e verificadas.
* Para cards de port/paridade cuja origem seja o React, a evidência de origem/paridade deve incluir o diff literal ou outra evidência direta do código React de origem, conforme definido no brief.
* Para cards sem origem React, exigir a evidência de origem equivalente definida no brief, sem inventar uma exigência de diff React.
* Quando testes automatizados forem parte dos critérios de conclusão, exigir o output bruto correspondente. Para testes XML, o output deve demonstrar 100% passing quando essa for a exigência do brief.
* Resumo em prosa nunca substitui uma evidência objetiva exigida pelo brief.
* Se uma evidência obrigatória estiver ausente, o card permanece em In Flight com uma nota objetiva do que falta.
* Nenhum worker marca o próprio card como Done. Só o revisor, quando houver revisão prevista, ou o Bruno podem fechar um card.

## Revisão

* Code Review não é uma etapa automática de toda execução.
* Um worker revisor novo, sem histórico da execução, só deve ser aberto quando:

  1. o Bruno solicitar explicitamente uma revisão; ou
  2. o card/brief original exigir uma etapa de revisão.
* Quando houver revisão prevista, o revisor recebe somente o necessário para avaliar o resultado, incluindo diff final e critérios de conclusão do brief original.
* O revisor aprova ou reprova com motivo objetivo.
* Aprovação → card pode ir para Done, seguida de ACK e release do worker que executou.
* Reprovação → card volta para In Flight com o motivo anexado.
* Se o objetivo explícito da Run for apenas implementação + testes + PR, sem revisão, a execução termina após a validação dos PRs e não deve iniciar Agent C.

## Escalonamento

* Se um worker sinalizar `question` ou `escalation` sobre decisão de escopo ou arquitetura não coberta pelo brief, pausar a tarefa e sinalizar o Bruno diretamente — não presumir a decisão e seguir.
* Questões operacionais que possam ser resolvidas pelo próprio brief, pelas skills do worker ou por evidências existentes devem ser resolvidas pelo Hermes sem interromper o Bruno desnecessariamente.
* O Hermes não deve implementar diretamente uma tarefa destinada a um worker para contornar uma dificuldade do worker.

## Memória de processo

* Decisões de arquitetura, abordagens que falharam, e blocos que estouraram tempo/ajustes vão para `~/.hermes/memories/herolog-process-memory.md`, não para este arquivo nem para o `AGENTS.md`.
* Ao registrar algo novo lá, seguir o mesmo filtro já usado na carga inicial: só decisão + motivo de processo, nunca detalhe de implementação/API.
* Informações estáveis sobre o funcionamento do Orca devem permanecer na `orca-orchestration-protocol`, não serem duplicadas aqui.
* Informações específicas sobre metodologia de implementação/paridade devem permanecer nas skills especialistas correspondentes.

## Estado final de orquestração

Ao fim de um ciclo de trabalho, confirmar:

* nenhuma decisão pendente;
* nenhuma escalação não resolvida;
* nenhum worker reclamável;
* todos os workers encerrados ou liberados conforme o ciclo definido;
* worktrees dos workers tratadas pelo mecanismo do Orca;
* PRs/entregáveis reais verificados conforme os critérios do brief;
* nenhum código foi alterado diretamente pelo Hermes quando a tarefa estava delegada a um worker.

Se a Run tiver sido explicitamente definida como
**implementação + testes + PR, sem Code Review**, o estado final esperado é:

**workers concluídos → entregáveis validados → PRs confirmados → workers liberados → STOP.**

Nenhum Agent C, Code Review ou merge deve ser iniciado automaticamente.
